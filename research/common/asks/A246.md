## 2nd-level analysis: what is genuinely new

Fildi's loop is agent-mediated: a human or agent proposes one study, Claude quant-reviews it, Cursor builds it, agents review the commit. The reel's loop is *closed and autonomous*: the system itself generates candidate strategies, backtests them, promotes or demotes them against a frozen baseline, and iterates — with humans setting the gates, not running each cycle. That closed loop does not exist in fildi today. The build is the loop machinery + the gates, not another single strategy.

## Use cases (why, expected value)

1. **Put-entry variant generation vs the Model List baseline.** Generate put-entry variants (strike width, DTE, delta target, entry filter) for the live put-selling book, backtest each against the current Model List baseline on identical data, promote only variants that beat baseline OOS. Why: the book's edge is variant selection, and manual studies test one variant per cycle. Expected value: a ranked variant queue with OOS evidence instead of one-at-a-time studies.
2. **One-change-at-a-time improvement on paper arms.** Take a live paper arm (e.g. S086/S088), propose exactly one change, test, keep or discard, log the decision. Why: this is the reel's "controlled" discipline, and it is currently done by hand per study. Expected value: faster iteration on arms that already have paper track records, with an audit trail of every kept/discarded change.
3. **Failure/regime analysis on paper ledgers.** When a paper arm underperforms, the loop diagnoses the losing regime (vol, trend, earnings window) and proposes a fix variant, tested before any adoption. Why: fildi's studies find edges; nothing systematically mines its own paper failures. Expected value: fixes sourced from fildi's own losing trades, not from outside ideas.

## Downstream impact

- Paper ledgers (promotion/demotion state per arm), Model List (gated entries only), Rankings/Track record (paper performance feeds both). No live-trading surface is touched. If a promoted variant ever reaches the live book, that is a separate Jamie decision, not a loop output.

## Upstream data dependencies + maintenance

- Bars/chains: existing Schwab → Yahoo live chain + nightly bars (Yahoo/FMP). LSEG/WRDS research lanes for features where licensed. Option history remains the known bottleneck (LSEG optlab sparse, ~1.3 strikes/name/date; Schwab-forward otherwise) — the loop must declare its history window per candidate and refuse candidates it cannot test.
- Maintenance: gate definitions live in one place (thresholds, OOS windows, cost model); baseline snapshots frozen per promotion round so "beats baseline" stays checkable; every generated candidate + verdict logged (kept/discarded + reason) so the loop is auditable, not a black box.

## Pass/fail bars (pre-registered, [quant] to tighten)

- FAIL if any promoted variant lacks a frozen-baseline comparison, an OOS window, or a cost-aware backtest (fees/slippage/spread).
- FAIL if the loop can place, or queue for placement, a live order (paper-only enforcement test).
- PASS bar: on a historical window, the loop reproduces a known study verdict (e.g. S082 PASS / S081 FAIL) from its own machinery — the loop must agree with Claude's verdicts before it is trusted with new candidates.
- PASS bar: at least one full generate → test → promote/demote cycle runs end-to-end on a paper arm with an audit log, zero human touches inside the cycle, gates enforced.

### Optimization: OpenJev + fildi's own cost architecture (mandatory, not optional)

- **OpenJev (A150 framework, done v1, registry `.agents/openjev/`):** local MLX on the Mac, $0 API cost, zero Claude tokens for inference. Use it as the loop's cheap pre-filter, never as final authority, never for price predictions, never with holdings/quantities/P&L/keys. Concrete uses: P11 (tier A, 0.987 failure-chunk retention) gates the loop's log/failure analysis so only flagged chunks reach the LLM; P10 (keeps 95.6% of needed files, skips 33% of irrelevant) triages code the loop reads; P21 overnight-put-risk (AUC 0.60, calibrated, best single question) is a diagnose-step feature for put names. Rules: read `--summary` aggregates, never dump raw `openjev_lab` rows (that is the waste mode); two-key verify (author cannot self-verify); auto-demotion on live misses. Do NOT use OpenJev for study search — P14 measured X (keywords 24/54 beat OpenJev 14/54). Constraint: OpenJev runs on the Mac (127.0.0.1:8091/8092); the VM cannot reach it, and the Mac sleeps — loop steps needing OpenJev run on the Mac on wake, and degrade gracefully (skip the pre-filter, do not block) when it is unreachable.
- **LLM only at the hypothesize step, on aggregates.** The loop's observe/diagnose steps output counts, quintiles, and regime splits; the LLM sees that summary, never per-trade text. Variant generation is deterministic (parameter grids), never LLM-per-candidate. This is what keeps the loop's token cost near the snapshot cost, not near a per-trade LLM cost.
- **Meter it with fildi's own meter.** `ai-pricing.ts` (A130) already prices LLM tokens and the audit found DB-cached LLM explains with per-user accounting; the loop logs its own token spend through the same meter, and a run that exceeds its budget pauses instead of spending.
- **Batch cadence, not live.** The loop runs in the nightly daily.py publish stage (like `strategy_signals.py`), after the LSEG refresh — never per tick, never per user request. Cost scales with the universe, not with users (the multi-user audit's snapshot finding).
- **Reuse, don't refetch.** Chain history (`option-chain-history.ts`), ATM IV snapshots (0024), LSEG `daily_history`, nightly technicals — the loop reads these; it adds no new vendor fetch.
