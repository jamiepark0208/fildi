# A233 — Fildi monetization: two-world split, data-supply rebuild, multi-user architecture

**From:** Muse → **To:** Grok (business model) + Claude (architecture / score feasibility)
**Date:** 2026-10-21 · **Status:** open · **Type:** strategy plan (no build authorized yet)

## 0. What Jamie asked

1. Ideas to make money off fildi.
2. Not all of his data may be accessible to other users — what stays private?
3. Is the app actually ready for many users, each with unique watchlists? Design for performance and speed at minimum cost, without violating external API terms.

Muse ran the diligence first: a code audit of cursor/mac-dev (22 surgical reads), competitor pricing checks, and vendor pricing checks (2026-10-21). Findings below are evidence, not vibes.

## 1. Audit verdict — multi-user bones exist; the data supply is single-tenant

**Already multi-user-ready (real, in code):**
- Invite-only auth: `users` table (bcrypt, roles admin/member), Postgres-backed sessions, rate-limited login/register (`lib/db/src/schema/index.ts:7`, `artifacts/api-server/src/routes/auth.ts`).
- Watchlist is user-scoped: `watchlist.userId` FK, every query filters by session user, per-user count cap enforced (`routes/watchlist.ts:18,24,298`).
- Score compute is batch snapshots, not per-request (`lib/scheduler.ts`, `fundScoreSnapshots` / `optionScoreSnapshots` tables) — **cost scales with the ~570-name universe, not with user count. This is the correct shape; keep it.**
- Market-data caches are shared, keyed by ticker, not per user (`live-quote.ts` 60s TTL; `options.ts` chains 30-min TTL) — users dedupe each other.
- LLM "Explain" is DB-cached by `ticker|surface|scoreHash` (shared across users) with per-user usage accounting in `ai_usage_log` (`lib/ai-explain.ts`) — LLM cost scales with distinct tickers, not users.
- Global vendor-usage ledger exists (`api_usage`, `fmp_api_usage`).

**Breaks or leaks if a second user logs in tomorrow:**
1. **All live market data rides Jamie's one personal Schwab account** — one token file (`~/.tradedash/schwab-tokens.json`, `schwab-auth.ts`), one client ID. Every member's quotes/chains flow through his account budget (`withBudget`). His 7-day re-auth outage = product-wide outage. Schwab's personal API terms do not contemplate serving third parties.
2. **Academic data is member-readable.** `routes/research-wrds.ts` gates on `requireAuth` only — any signed-in user can read IBES/SUE from `wrds_research`. The schema itself says "Academic / non-commercial… sole-user." Same pattern to verify on `research-lseg.ts`. **This is a live license-exposure bug the moment anyone else is invited — before any monetization.**
3. **The real book has no user dimension.** `portfolio_options/positions/orders/account_summaries` are keyed by snapshot + free-text account, no `user_id`; routes are admin-gated instead. Safe today; structurally cannot offer members "your book."
4. **Model List is welded to Jamie.** `MODEL_LIST_USER_ID = 1` (`routes/watchlist.ts:146,406`) — built from user 1's holdings/buying power.
5. **All vendor keys are personal accounts** (FMP, Finnhub, Polygon/Massive, Alpha Vantage, Anthropic) — shared quotas; one heavy user starves everyone; retail tiers typically prohibit redistribution/display in a commercial product.
6. **Single-process ceiling:** in-process TTL caches, in-process scheduler, token file on disk, no Docker — horizontal scaling would multiply upstream calls and risk double-running jobs. Fine at one instance; named here so nobody scales it naively.
7. Watchlists are **social by default**: any signed-in user can view another's watchlist (`GET /watchlist/user/:username`). A paying product must choose this deliberately, not inherit it.

## 2. The two-world split (privacy + licensing in one move)

| | World P — Jamie private, never ships | World S — sellable product |
|---|---|---|
| Book | `portfolio_*` tables, Robinhood book, journal, P&L | Members' own books: CSV/manual import into user-scoped tables (v1); per-user broker OAuth only if a broker offers a real third-party program |
| Market data | His Schwab connection (powers his instance only) | Commercially licensed feed (see §4) under a product-owned vendor account |
| Research | WRDS/LSEG lanes, A85 receipts, study results (S-series), his score tuning | Public/commodity inputs only: licensed estimates/fundamentals; **fund score needs a commercial variant with IBES-derived inputs removed or replaced** (IBES revision breadth + SUE currently feed it — A228) |
| Features | Model List from HIS holdings, position odds on his book | Each member's own model list from THEIR imported book (after T2 fix) |
| Agents | ASKS queue, agent roster, briefs pipeline | None of it. Ever. |

Rule of thumb for every future feature: if it touches World P data or an academic/personal license, it is Jamie-only by construction (separate routes, admin gate, separate schema), not by policy text.

## 3. Monetization models — ranked

Competitor anchors (checked 2026-10-21): Unusual Whales Free(delayed)/ $50 / $75 / $120, API sold separately $150–375; OptionStrat Free(15-min delay) / $39.99 / $99.99; FlowAlgo $149; Cheddar Flow $85–99; Trade Ideas $89–178. Universal pattern: **free tier on delayed data → paid = live data + scanners + alerts → API upsell.** Nobody in the comp set owns "the premium-seller's cockpit" — assignment risk, DTE posture, event windows, strike discipline, book-level risk (A221 territory). That is fildi's differentiated wedge: it was built by running a real put book.

**M1 — Tiered SaaS (primary recommendation).**
- Free: delayed data, 1 watchlist (≤25 tickers), yesterday's score snapshots, pundit tracker. Purpose: funnel + SEO, near-zero marginal cost (delayed tier data).
- Pro ~$49/mo (annual ~$490): live quotes/chains, full scores, options tools (IV walls, structures), event windows, own-book import + risk view, alerts.
- Max ~$99/mo: everything + accountability/model-list features on own book, higher watchlist/chain budgets, priority data freshness.
- Pricing sits deliberately under UW Max / FlowAlgo, above OptionStrat Tools — justified by book-management features neither has.
- Break-even sketch (data anchors §4): delayed stack ≈ $180–250/mo → ~5 Pro users cover data+infra. Real-time stack ≈ $500–700/mo → ~12–15 Pro users. The business is not data-cost-constrained at these prices; it is distribution-constrained.

**M2 — Bring-your-own-keys license (parallel, zero data cost).** Sell the software (self-host or managed single-tenant) where the user plugs in their own broker/data keys and runs their own instance. No redistribution problem exists — each user is their own data licensee. Smaller market, near-zero marginal cost, perfectly aligned with the privacy split. Also the natural offer for privacy-paranoid traders — Jamie's own tribe.

**M3 — Community / cohort white-label.** One license per trading community, Discord, or newsletter: their members get World S under the community's brand; community owner is the customer. Distribution solved by the partner. Price per seat or flat per community; terms set per contract.

**M4 — API tier (later).** Scores/signals as an API once M1 proves demand — UW charges $150–375/mo for exactly this. Do not build first; it commoditizes the wedge and invites scraping.

**M5 — Content funnel, not a product.** The twice-daily briefs + pundit tracker (public voices only, no World P data) as free content that feeds the M1 waitlist. Jamie already produces this daily at zero extra cost.

**Never sell:** his live positions or book in any form; anything derived from WRDS/LSEG; Schwab-powered data to anyone; the study corpus/results as "signals" (see regulatory flag).

**Regulatory flag (needs counsel, not vibes):** selling scores is generally tool publishing; selling a model list derived from his own trades, or anything personalized to a member's book, moves toward investment-adviser / publisher territory (SEC/state). Keep v1 framed and built as tools + education, no personalized recommendations, standard disclaimers, and get a securities lawyer's hour before charging. This is a design constraint, not a footnote.

## 4. Product data supply — the rebuild that makes World S legal

Replace personal keys with product-owned commercial agreements; the app already has the right cache/snapshot architecture to make this cheap:

- **Quotes/bars:** Massive (ex-Polygon) — individual anchors: Stocks Starter $29/mo (15-min delayed, unlimited calls), Advanced $199/mo (real-time SIP). Business/display use is priced separately — get the commercial quote; the architecture (one fetch per ticker per TTL window, batched) means call volume is a non-issue, so negotiate on display rights, not calls.
- **Options chains:** Massive Options Developer $99/mo (OPRA delayed) for the free/delayed tier; Options Advanced $249/mo (OPRA real-time) for paid tiers. OPRA real-time display also carries per-user subscriber fee mechanics — confirm pass-through treatment in the vendor agreement (verify item, not assumed).
- **Fundamentals/estimates (fund-score commercial variant):** FMP Premium/Ultimate ($49–139/mo anchors) — display/redistribution requires FMP's separate commercial agreement (their own docs say so). Estimates feed replaces IBES in World S; expect the commercial-variant score to differ slightly from Jamie's — measure the delta once, disclose internally, never blend the two scores' histories.
- **Yahoo is out** of World S entirely (no commercial redistribution right). Schwab stays World P only.

**Performance/cost design (how many unique watchlists stay fast and cheap):**
1. **Demand universe, not user count, drives fetches:** fetch set = scored universe ∪ (union of all members' watchlists), maintained as one shared set. 100 users with overlapping large-cap watchlists cost barely more than 10.
2. **One fetch, all users:** keep ticker-keyed TTL caches (60s quotes / 30m chains already in code); when the app moves server-side (A72), back the cache with the DB/Redis so multiple processes share it — until then, single instance is a *feature* (cache coherence), not a limitation.
3. **Scores stay batch:** nightly + intraday snapshot cadence for the universe; a member's exotic off-universe ticker gets on-demand scoring queued into the next batch, not a synchronous per-request pipeline (bounds worst-case cost per user).
4. **Per-user budgets:** extend the existing global `api_usage` ledger to per-user daily chain-call and LLM-explain budgets by tier; watchlist caps already exist — set them per tier. One abusive user degrades only their own budget.
5. **Freshness is a tier feature:** delayed (free) vs 60s-cache live (Pro) vs fastest cadence (Max) — the TTL knobs already exist; pricing maps onto them directly.

## 6. Roadmap

- **P0 — Lock the doors (now, ~zero cost):** T1 + T4. Pass bar: leak checklist clean. This is owed even if monetization never happens — the app already has invite codes.
- **P1 — Data-supply validation:** commercial quotes from Massive + FMP (display rights in writing); build the fund-score commercial variant in shadow and measure its delta vs the IBES-fed score on the scored universe. Pass bar: variant rank-correlation ≥ 0.9 vs production on a 4-week window, or the variant gets its own honest name/labels — never silently swapped.
- **P2 — Tenancy completion:** T2, T3, T5 on the server instance (A72). Pass bar: two test members with disjoint watchlists + imported books see only their own data; shared-cache hit rate ≥ 80% on overlapping tickers during market hours.
- **P3 — Billing + tiers:** Stripe subscriptions (Jamie already runs Stripe tooling), tier gates mapped to TTL/budget knobs. Pass bar: free member cannot reach a live-data or over-budget response under load test at 50 concurrent members.
- **P4 — Launch:** waitlist from M5 content; M2 offered in parallel from day one (it needs no data rebuild — T1/T4 only). Pass bar for calling it a business: 25 paying members or 3 M2 licenses, else it stays a private tool with a paid door — a fine outcome, stated in advance so nobody rationalizes later.

## 7. Risks

- Distribution, not technology, is the constraint — the comp set has 50k+ user funnels; fildi's wedge is depth for premium sellers, a smaller, richer niche. M3 exists to borrow other people's funnels.
- Regulatory (§3 flag) — resolve before P3, not after first revenue.
- Schwab remains a single point of failure for Jamie's own instance regardless — A72/A73 work continues independently; World S must never inherit that dependency.
- Score-variant drift (P1) — if the commercial fund score is materially weaker, the honest product is M2 (software, user brings data) first and M1 second. The plan survives that verdict.

## Revision — 2026-10-21, Jamie's correction (supersedes the framing in §2, §4, §6-P1, §7)

Jamie's call: the "commercial variant / World S rebuild" framing is too coarse — a first-order barrier treated as a product fork. Fildi already solves this exact pattern for market data (Schwab → Yahoo fallback chains, source-labeled; A63 ranking). Generalize it:

**Per-component source chains.** Every component that consumes data declares an ordered source chain *per user class* and degrades down the chain instead of failing or blocking the product:
- **Jamie class:** research/personal sources first (WRDS IBES, LSEG StarMine, his Schwab), falling back to Yahoo / Finnhub / FMP as the app does today.
- **Member class:** licensed sources only (Finnhub, FMP, Massive tiers) — same component, same UI, different chain.

**Research-only components are hidden, not rebuilt.** A component whose only lawful source for members is none (WRDS/LSEG panels) carries a per-class entitlement flag in a component registry, enforced server-side; members simply never see it. T1 in §5 is accordingly reframed: not "gate two routes" but **entitlement gating per component**, with the route audit (permission verification, running 2026-10-21) supplying the component inventory.

**Fund score reframed: one component, two chains.** Jamie chain = IBES revision breadth + SUE (current production). Member chain = licensed estimates data (e.g., FMP estimates/revisions) computing the same fields. The §6-P1 measurement survives as a *chain-quality check* (member-chain vs Jamie-chain rank correlation ≥ 0.9 over 4 weeks) — not a product fork, and the two chains' outputs are never blended in one history. Components display their active source (fildi already labels data sources; extend the label to the chain level).

**Yahoo caveat (Muse, for the record):** Yahoo serves Jamie's class under personal use; the member chain must not rely on Yahoo in a paid product (no commercial display right). Finnhub / FMP / Massive licensed tiers fill that slot. The fallback principle stands; the member chain's members change.

**What this kills:** the "score can't be sold as-is, rebuild World S" framing, and with it most of §4's separate-supply build. World S = the same app with member-class chains wired + entitlement-hidden components. Cheaper, faster, and it is how the app was already built. Remaining genuinely-new work: the component registry + entitlement flags, the member-chain wiring for the handful of components that consume research data, and product-owned vendor accounts (T5). Reviewers: judge the plan as revised; Grok in particular — attack whether per-component chains create a support/consistency burden worse than the fork they replace.
