# A258: forecast_ledger.resolve: one bad row aborts the whole run — per-question isolation
**From → to:** Muse → Cursor · **Date:** 2026-10-24 · **Status:** planned
**Source:** Muse code review 2026-10-24, finding H7 (High).

## Ask
Isolate ledger resolution per question so one corrupt row can never roll back a whole batch again.

## Detail
Evidence: `scripts/watchlist_sync/forecast_ledger.py`, `resolve()`: the loop does `float(meta["strike"])` unguarded and `conn.commit()` only at the end. One corrupt `meta` (missing strike) raises mid-loop, rolling back every resolution already processed, and the same row aborts every subsequent run. (The `resolves_on < today` one-day lag is documented in the header — intentional, not part of this fix.)
Fix direction: try/except per question, log-and-skip the bad row, commit per question or batch.

## Pass/fail
- Fixture with one corrupt `meta` row: all other resolutions persist, the bad row is logged and skipped, and a rerun progresses past it.
- Existing ledger tests pass.

## Reviews

Uses: (1) nightly put and index grades have to land; (2) a missing strike is a data bug; (3) the next night must get past that row; (4) missed — the extra resolvers in the same loop throw too.
Overlap: `resolve` casts `meta["strike"]` with no guard and commits once at the end. Helper tests do not cover this loop. Leave the one-day resolve lag as it is.
1. Moves: ops (ledger grades complete).
2. Savepoint per question. On any error, roll back to the savepoint, log the question id, continue. A bare try/except leaves the database transaction aborted, so the rest of the batch still dies.
3. Write the error onto that question once and skip it next run. A row that can never resolve must not be retried every night.
4. Fixture: one missing strike, two good questions. Both good outcomes persist; the bad row is skipped; a second run does not raise and does not undo the good rows. Existing ledger tests stay green.
