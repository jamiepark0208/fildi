## Ask (Jamie 11-07, condensed)
We pull from many sources. Fetch history once (ad hoc), then routine jobs fetch only the missing tail, not everything every time. Make it safe: every heavy fetch or processing step first checks whether it is needed (e.g. max(as_of) vs the newest expected date — "not the only way").

## Detail
### 1. One guard helper (one home: `scripts/fetch_guard.py` + `artifacts/api-server/src/lib/fetch-guard.ts`, same contract)
`plan_fetch(source, table, key, date_col, cadence)` →
- watermark = `max(date_col)` for that key (one query for all keys, not one per key);
- expected = last trading day the cadence promises (reuse the calendar in `data_freshness.py`);
- returns `skip` (watermark ≥ expected), `tail(from=watermark+1 or minus a small overlap for restatements, to=expected)`, or `backfill` (no rows) — **backfill only runs with an explicit `--backfill` flag**; routine runs log and skip it.
- Slow-changing data (SEC companyfacts, IBES, fundamentals): check a cheap change signal first (EDGAR submissions `filings.recent` newest accession date / vendor last-modified / ETag) and fetch only when it moved.
- Writes: upsert with `WHERE (excluded.*) IS DISTINCT FROM (t.*)` (Postgres) so unchanged rows don't rewrite.
- Every run writes one row to `fetch_runs` (source, job, keys planned/skipped/fetched, calls, rows inserted/changed, seconds). That's the before/after meter.

### 2. Heavy-step guard
Long processing (rebuilds, replays, panel builds, sweeps): skip when inputs' watermarks + code hash are unchanged since the last successful run (store in `fetch_runs`). `--force` overrides. Budget line per job: max calls and max minutes; exceeding aborts with a clear message.

### 3. Apply to jobs, worst first
1. schwab-1m-poll: request only since last stored ts (minus 2 bars), distinct-only upsert.
2. LSEG daily_history, WRDS ibes_statsum / crsp_dsf loaders: tail window from watermark.
3. prices_historical writers (+ split_repair touches only split tickers), lab_fund_features (recompute only new dates).
4. SEC companyfacts: fetch only when submissions show a newer filing; vendor_raw stores a new row only when the payload hash changed.
5. Inventory pass: every scheduled job (`scripts/maintain.mjs`, launchd `com.fildi.*`, api-server schedulers, `watchlist_sync/daily.py`) → table in `research/common/data-inventory.md` § Fetch mode: job · source · mode (tail / change-signal / full) · guard yes/no. Any remaining `full` needs a one-line reason.

### Acceptance (measured before/after, 2 trading days each)
- `fetch_runs` populated for every scheduled fetch job.
- intraday_bars_1m updates/day ≤ 1.2 × new rows/day (today ~2×+); ibes/daily_history/crsp updates/day ≈ new rows only.
- Vendor calls/day per source not higher, no table goes stale (`data_freshness.py` clean).
- Tests: guard returns skip / tail / backfill correctly on fixtures; routine run without `--backfill` never fetches history; distinct-only upsert leaves updated_at unchanged for identical rows.
- AGENTS.md 8c gains one line: "fetch the tail from the watermark; backfill only with `--backfill`; use `fetch_guard`".
