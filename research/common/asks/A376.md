## Ask
Fix the A369 trade cache so it actually hits, and two Mediums in the same commit (OPRA cache equivalence, leak detector). The cache's whole purpose — skipping 56 full strategy runs per sweep — is currently void.

## Detail
- **H1 — Trade cache key uses salted `hash()`; it can never hit across processes.** `conditional_engine.py` `_a359_cache_path` (~L1187): key is `abs(hash(key)) % (10**10)` on a `str`; CPython string `hash()` is randomized per process (verified: the same string hashes to two different values in two processes). Every fresh process computes a different path, the cache returns `None`, the sweep rebuilds, and orphan parquets accumulate. Same function / meta (~L1250–1260): the key and `*_meta.json` carry only tickers + row counts — no code version, spread-calibration version, thresholds, exits, or data date — so once the hash is fixed, a stale cache (e.g. pre-2fdd403 spreads) will be silently reused. Fix: `hashlib.sha256` over tickers + a version string, verified in meta. Pass: two separate processes resolve the same cache path, and a spread-calibration change invalidates the cache.
- **M1 — Cached OPRA-window rows ≠ legacy OPRA rows for multi-session exits.** `run_threshold_sweep_from_cache` (~L1260+): the cached path filters stored trades post-hoc by `in_opra_window`; the legacy path runs `session_filter` before simulation. Positions carry across sessions, so for `tp50_overnight` / `hold_expiry` exits the filtered cache cannot reproduce the session-filtered run. Equivalent only for `same_day` exits. Fix: restrict the cache path to `same_day`, or store session-filtered runs. Pass: cached and legacy runs agree on an overnight-exit cell.
- **M2 — Leak detector misaligned / mis-signed (needs a run to confirm the outcome).** `study_leak.py` `is_planted_lookahead` (~L55) + `conditional_engine.py` `run_conditional_leak_test` (~L1946): the detector pairs entry bar `i` with `rets[i]` (the return ending at `i`), but the planted signal at `i` uses RSI[i+1], so its edge lives in `rets[i+1]`; the shifted entry actually captures that next-bar move. It also flags only when `mean(clean) > mean(shifted) + 0.002` (long-side positive returns) while the strategy is short puts (edge = negative forward returns). It may flag/pass for the wrong reason. Fix: align the detector to `rets[i+1]` and the short-put sign, then run the planted-leak test and report the flag. Pass: the planted leak is caught and a clean run passes.
