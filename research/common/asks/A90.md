# A90 — Sector-specialist reader agents (parallel readers + committee, not chatty crews)

**Status:** open
**From:** Muse → Cursor
**Date:** 2026-10-14
**Severity:** medium

## Context
Jamie asked (Oct 14): should fildi use sector-specialist agents like hedge-fund research analysts —
one agent per sector with optimized context (firms, trends, events, catalysts, risks), or a
database-team agent? Research on role-specialized agent teams completed Oct 15.

## Research headline
- Patterns: supervisor/worker (best-supported), CrewAI role crews (3–5× more LLM calls from agent
  "negotiation"), LangGraph explicit graphs (lowest tokens/latency), MoE-style routing.
- **Evidence is sobering**: multi-agent average gain −3.5%; sequential agent work 39–70% worse than
  a single agent; gains only for genuinely parallel decomposable work (+80.8% on financial
  reasoning). Multi-agent uses 3–10× tokens; ~64% of pipeline tokens can be pure coordination
  overhead; each handoff is a lossy telephone game.
- Specialization wins for: independent parallel research, separate permissions, real verification
  steps. Real deployments: per-employee agents (Two Sigma), hypothesis-generation agents (Man Group).
- **Verdict: parallel specialist READERS + committee aggregator + deterministic risk-manager gate is
  worth doing. 18-agent debate ensembles, hierarchical crews, per-domain fine-tuning are excessive.**

## What to build
1. **Sector readers**: one lightweight reader per sector (or sector group) — narrow prompt, narrow
   data sources (sector news, earnings, filings), emits a structured sector brief (trends, events,
   catalysts, risks). Runs in parallel; no inter-agent chatter.
2. **Committee aggregator**: combines reader briefs into scores (not raw context) — deterministic
   aggregation, no LLM negotiation.
3. **Risk-manager gate**: deterministic rules (existing risk ceilings) have final say — the
   committee advises, the gate decides.
4. **Database steward** (the "database team" agent): owns schema hygiene, backfill jobs, data-quality
   checks — narrow, well-defined, high value.

## Acceptance
- [ ] Sector readers run in parallel with bounded context each; no agent-to-agent messaging.
- [ ] Aggregator is deterministic; token cost measured vs single-agent baseline.
- [ ] Risk gate unchanged and final; readers are advisory only.
- [ ] DB steward owns the data-quality checklist currently done ad hoc.
