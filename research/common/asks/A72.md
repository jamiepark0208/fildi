# A72: Fildi live-server migration — private always-on app (phased, iterative)
**From → to:** Muse → Cursor · **Date:** 2026-10-12 · **Status:** open

## Ask
Design and execute a phased migration of fildi from Jamie's MacBook to an always-on server, so the app is usable from any browser and his phone as a private app — without draining his Mac's battery. Production-harden the code, processes, scripts, and monitoring along the way, and establish dev/staging/prod environments. Each phase ships independently; later enhancement waves iterate on the live system.

## Thesis
Fildi only works when Jamie's Mac is awake — scheduled tasks, the API, the DB, and every automation die with the lid. That single constraint blocks the options-book brief, 24/7 monitoring, and phone access. A small always-on server removes it for ~$0 (Oracle free tier) while the Mac returns to being a dev machine. This is the highest-leverage infra move available: every automation row (A46–A70) gets more valuable on an always-on host.

## Why now
- The queue is shifting from research rows to live automation (briefs, Model List verify, scheduler trust). All of it assumes the host is awake.
- Jamie explicitly asked for phone/browser access anywhere and a production-ready posture with environments.
- Schwab re-auth just happened — the token story is fresh; solve the server-side OAuth callback now, once.

## Goals / non-goals
Goals: (1) fildi reachable privately from any browser + phone, 24/7; (2) Mac battery untouched — server does all scheduled work; (3) prod-hardened: secrets, backups, monitoring, restarts; (4) dev/staging/prod parity via containers; (5) phased, each phase independently shippable and reversible.
Non-goals: public multi-user SaaS; rewriting the app; changing the quant/scoring logic; anything that touches brokerage credentials beyond the existing Schwab OAuth.

## Current-state inventory (verify in Phase 0)
- API server: `artifacts/api-server` (Express). Frontend: `artifacts/stock-compare` — confirm serving model (same process vs separate).
- DB: local Postgres (`DATABASE_URL` in `.env.local`; local-only per DB audit). Tables include `prices_historical` (source-tracked), portfolio_*, `option_score_snapshots`, `desk_commentaries`.
- Scheduler: in-process (`lib/scheduler.ts`) + local node processes; tasks assume macOS paths (`~/.tradedash/`, `/tmp/fildi-logs/`).
- Secrets: `.env.local` (Schwab client id/secret, DB URL, vendor keys). Tokens: `~/.tradedash/schwab-tokens.json` (mode 600).
- Schwab OAuth: callback `https://127.0.0.1:8182` (must match Schwab dev portal exactly); refresh token dies every 7 days → weekly browser re-auth.
- Cron-like jobs driven from outside (Muse-side crons) hit the local API — these keep working against the server URL instead.

## Target architecture
```
[Phone / Browser anywhere]
        │  Tailscale (private mesh VPN, no public ports)
        ▼
[Oracle Cloud ARM VM — free tier: 2 OCPU / 12 GB RAM (new signups since Oracle's Jun 2026 halving; was 4/24)]
  ├─ prod stack (docker compose): api-server + frontend + postgres (volume) + scheduler (in-process)
  ├─ staging stack (docker compose, separate project): same images, separate DB
  ├─ Caddy (TLS, serves only on tailnet)
  ├─ backup cron: pg_dump → Oracle object storage (free 10 GB) + local volume snapshot
  └─ health endpoint → uptime monitor → alerts to Jamie
[MacBook] = dev machine only. Weekly Schwab re-auth via server callback URL.
[Muse-side crons] = unchanged, retargeted at the server's tailnet URL.
```

## Access model (private app)
- **Tailscale** on the server + his phone + Mac. The app is reachable only on the tailnet — no public IP exposure, no login-page-on-the-internet risk.
- Caddy terminates TLS with a tailnet hostname (e.g. `fildi.tail-scale.ts.net`).
- Later enhancement wave: add app-level login (OAuth or password) if he ever wants public access. Not Phase 1.

## Phase 0 — Prod-readiness audit (no infra yet)
Twelve-factor checklist against the repo; output is a punch list, not code:
1. Secrets: enumerate every env var; nothing secret committed; define server secret layout (`.env.prod`, mode 600, deployed over SSH, never in git).
2. Paths: find all `~/`, `/tmp`, hard-coded ports, macOS-only assumptions; make them env-configurable.
3. Ports/serving: confirm how stock-compare is served; single-port target behind Caddy.
4. Scheduler: confirm it survives process restarts (idempotent jobs, no in-memory-only state); document what "fresh" means per job.
5. Logs: structured logs to stdout (Docker captures); stop writing critical state only to `/tmp`.
6. Schwab OAuth: design server-side callback flow (new redirect URI registered in Schwab dev portal — needs Jamie; weekly re-auth unchanged, just pointed at the server).
7. DB: confirm Postgres version, extensions, size; pg_dump restore tested locally.
8. Backups: define RPO/RTO (suggest: daily dump, 7-day retention, restore tested).
9. Health: define `/health` (API up, DB reachable, scheduler alive, Schwab days-left) — the existing `/api/schwab/status` feeds into it.
Acceptance: punch list filed as a checklist row; zero code changes.

## Phase 1 — Containerize
- `Dockerfile` for api-server (node, prod deps only, non-root user), frontend build served statically or via API (per Phase 0 finding).
- `docker-compose.yml` (prod shape) + `docker-compose.staging.yml`; Postgres as a service with named volume; env via `.env.prod` (gitignored).
- `make`/`pnpm` scripts: `prod-build`, `prod-up`, `prod-logs`, `prod-backup`, `prod-restore`.
- Acceptance: `prod-up` on a clean Linux VM (or Jamie's Mac Docker) boots the full app; health endpoint green; no host-specific paths.

## Phase 2 — Environments
- dev: Mac as today (unchanged workflow).
- staging: second compose stack on the prod VM (different ports, separate DB, seeded from prod backup).
- prod: the live stack.
- Promotion: build once → same image to staging → smoke tests → prod. Tag images by git sha.
- Acceptance: a trivial change flows dev → staging → prod with the documented commands; staging never touches prod data.

## Phase 3 — Prod deploy (needs Jamie: Oracle account)
1. Provision Oracle ARM VM (Ubuntu), harden SSH (key only), install Docker + Tailscale + Caddy.
2. Deploy prod stack; join tailnet; verify private-only access (no public listeners).
3. Register new Schwab redirect URI in Schwab dev portal (Jamie does the portal click; Cursor preps the exact URI + callback handler).
4. Cut over Muse-side crons to the tailnet URL.
5. Acceptance: app loads on phone (Tailscale) and Mac browser; API + scheduler green for 72h; Schwab re-auth completes through the server callback.

## Phase 4 — Data migration + cutover
1. Freeze Mac writes; pg_dump; restore to prod; verify row counts + `max(updated_at)` per key table.
2. Dual-run window (≤48h): Mac stack read-only, prod live; compare brief outputs.
3. Cutover: prod primary; Mac stack stopped (kept as emergency rollback for 2 weeks).
4. Rollback plan documented before cutover.
- Acceptance: zero data loss (row-count parity), one full weekday cycle clean on prod, rollback tested once.

## Phase 5 — Monitoring hardening
- Uptime monitor (external, e.g. UptimeRobot free) → alerts on downtime.
- Log aggregation on the VM (Docker logs + rotation; alert on ERROR spikes).
- Backup verification job (weekly restore-to-staging test).
- Oracle idle-reclamation keepalive.
- Wire the existing Muse-side watchers (repo watch, mac-health → server-health) to the new host.
- Acceptance: simulated failure (stop API container) pages within 5 min; backup restore proven monthly.

## Phase 6+ — Iterative enhancement waves (post-live, prioritized with Jamie)
Candidates, each its own row later: mobile-first UI pass for phone use; push notifications for briefs/alerts (replace/augment chat delivery); public-access option with login; perf pass (the A64/A65 class); multi-user later — explicitly out of scope now.

## Risks
- Oracle reclaims idle free instances (PAYG signup is exempt; keepalive + external monitor stay as backup) → documented re-provision (infra-as-script, not clicks).
- Schwab portal changes / callback mismatch → test OAuth on staging first; keep localhost flow as fallback.
- Secret leak in transit → SSH-only deploy, 600 perms, never in git/CI logs.
- Scope creep → hard phase gates; Jamie approves each cutover.
- Weekly Schwab re-auth persists (Schwab policy) — unchanged burden, server doesn't fix it; the Sunday reminder cron stays.

## Cost
Infra: $0 (Oracle free tier; card on file, no charge). Time: Cursor build phases; Jamie: Oracle signup + Schwab portal click + Tailscale install on phone (~30 min total).
