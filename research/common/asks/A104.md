## What Lightpanda is (verified from repo)
- Headless browser written **from scratch in Zig** — not a Chromium fork. Built for AI agents
  and automation.
- Published benchmarks (933 real pages, EC2 m5.large): **~16x less memory** (123MB vs 2GB per
  100 pages), **~9x faster** (5s vs 46s per 100 pages) than headless Chrome.
- Drop-in via CDP on port 9222 — Playwright/Puppeteer/Chromedp compatible; `fetch --dump
  markdown/html/png` one-liners; Docker one-line install; native MCP server + agent skill.
- Agent mode: LLM-driven browsing that records deterministic PandaScript (prototype with the
  model, ship without one at runtime).
- Status: JS support via V8, Web Platform Tests in progress — not full Chrome compat. Nightly
  builds; maturing, not mature.

## Why it fits fildi
- **A72 server RAM**: the Oracle free tier has 12GB. Scrapers running at 123MB instead of 2GB
  per 100 pages is a real constraint win on that box.
- **JS-rendered sources**: fildi's scrapers mostly use APIs/RSS, but the JS-rendered gaps
  (holdings pages, consulting reports, Fed speeches) currently need a full browser or fail.
- **License**: AGPL-3.0 — fine for internal scraping use; flag before embedding in anything
  distributed. Telemetry on by default — disable via `LIGHTPANDA_DISABLE_TELEMETRY=true`.

## What to build (phased)
- **Phase 1 — inventory**: where does fildi use browser automation / JS rendering today?
  (List every scraper that shells to Chrome/Puppeteer/Playwright or fails on JS pages.)
- **Phase 2 — pilot on one source**: run Lightpanda against one JS-rendered source
  (candidate: a holdings page or consulting outlook page), diff output vs current method.
  Pass bar: correct output + the memory/speed win on the Oracle-sized box.
- **Phase 3 — adopt as standard scraper engine**: replace headless Chrome where the pilot
  wins; document per-site WPT caveats (sites with heavy JS frameworks get tested individually).
- **Phase 4 (later)**: evaluate agent mode + MCP server for agent-driven browsing tasks.
