# A323 — Settings catalog freshness: registry-driven rows + backfill post-Oct-24 tools
**From → to:** Muse → Cursor · **Date:** 2026-11-02 · **Status:** planned

## Ask
Make the Settings vendor catalog self-updating so a tool can never again be "set up but invisible": registry-driven rows, plus a backfill of the tools added after the Oct 24 inventory. This is the systemic fix behind the A320–A322 verdicts — without it, every future adoption needs another manual inventory project.

## 1st-level analysis (what happened)
- The catalog panel (VendorCatalogPanel, under API Monitor) renders `/api/admin/data-sources`, fed by the A263 (Oct 24) catalog + the `data_sources` table + `api_usage` (A264, shipped Oct 25).
- Tools added after Oct 24 have no guaranteed row: Caldara–Iacoviello GPR (10-28, → `watchlist_sync.macro_daily`), Treasury Fiscal Data (10-28, → `watchlist_sync.gov_flows_*`), D1 desk-facts (11-02, → Daily News panel). Future adoptions (LSE post-validation under A319, Chronos/FinBERT post-adoption under A320/A321) would face the same lag.
- The panel is fine; the feed is frozen. The fix is a contract, not another inventory.

## 2nd-level analysis (why it matters)
- A catalog that lags reality recreates the exact failure Jamie flagged: tools exist, nobody can see them, nobody uses them, and the next audit rediscovers them as mysteries.
- The contract flips the default: a new source appears in Settings by construction when it is built, because its plan's acceptance criteria include its registry entry. Visibility stops being a separate project.

## Use cases
- **UC1 — Backfill the three orphans.** GPR, Treasury flows, and D1 desk-facts each gain a catalog row (what it feeds, volume, limit) without touching panel code. Expected value: the panel stops lagging reality on day one.
- **UC2 — Future-tool proof.** Add a fake source in a test → panel shows it; remove → gone. Expected value: A319/A320/A321 adoptions land visible by construction, and the next "why isn't X in Settings" question answers itself.
- **UC3 — Living Unused column.** The registry entry carries the "unused" field, so the panel's Unused column stays current as endpoints get adopted (e.g., Polygon Form 4 if S099 lands it, Schwab movers if S097 lands them). Expected value: "available, not used" becomes a living list, not a stale audit.

## Steps
0. Backfill rows for GPR, Treasury Fiscal Data, and D1 desk-facts with honest values (feeds: macro_daily table / gov_flows tables / Daily News panel; limits: none/public; metering: job-run counts or n/a where no meter exists — never invented numbers).
1. Implement the registry contract: a `data_sources` registry entry (table + code entry point) that `/api/admin/data-sources` reads, so a new source renders in the panel with no panel-code change. Metering hook included where the source has one; n/a declared where it doesn't.
2. Test: synthetic source appears in the panel, then disappears on removal. The test — not an assertion — proves the contract.
3. Update the repo's plan checklist (AGENTS.md plan template or equivalent) so every future tool row must name its catalog-row criterion as acceptance. A tool plan without a catalog criterion is incomplete on its face.
4. Reviewing agent (Claude, ≤20-line summary when pool recovers): propose 2+ additional use cases from these worked examples before the row closes. Grok may red-team the registry design (e.g., what stops a stale registry entry from outliving its source — answer: the entry's owner + re-check date, same rule as A322).

## Downstream impact
- Settings › API Monitor catalog gains the backfill rows and the registry mechanism. No panel redesign; the panel renders what the registry says.
- Future tool rows (A319 follow-up, A320/A321 adoptions, A322 keeps) inherit visibility automatically.
- The A263 inventory file stays a frozen Oct 24 reference; it is not rewritten. The registry is the living record from here on.

## Upstream data dependencies + maintenance
- A263 catalog (frozen reference), `data_sources` table, `api_usage` metering, job-run metadata for the backfilled tools.
- Registry entries carry owner + re-check date; a future inventory verifies them instead of rediscovering them.

## Pass / fail bars
- **P1.** All three backfill rows visible in Settings with honest feeds/limits/metering.
- **P2.** Synthetic-source test passes: appears on add, disappears on remove, with zero panel-code change.
- **P3.** Plan checklist updated: catalog-row criterion required for future tool rows.
- **P4.** No invented numbers: every backfilled metering value traces to a job count, a meter, or an explicit n/a.
- **Stop rule.** A design where adding a source still requires a panel edit = fail, not "mostly registry-driven."
