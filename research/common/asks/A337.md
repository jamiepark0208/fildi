## 1. Goal (Jamie's words, distilled)

Jamie wants a journal section inside the fildi app: a place to babble his thoughts and reflect on the day, keep track of historical stuff, and write more. Because he writes loosely, the pipeline is two agents, not one:

- **Agent 1 — the optimizer.** Reads his babble and restructures it into a clean task/goal for the next agent: concise, filler removed, the real goal stated. Not just reorganizing — truly understanding the goal **and how to verify success continuously** (success criteria + a check that keeps running).
- **Agent 2 — the context agent.** Reads the optimized tasks plus his journal history and adds its own comments on how it can help: keep his trade ideas tight, check his Robinhood book is safe / well positioned, run new studies from his market views, or propose plans for new features. It looks for ways to help him and fildi, with the journal as its context.

Flagship example he named: **self-recursive learning** — fildi's model giving better trade recommendations by learning from its own outcomes. He is sure other people on GitHub have done this, and wants to know how to evolve it.

## 2. Muse 1st-level analysis

This is three things that must ship as one system, not three features: (a) a capture surface (journal UI + storage), (b) a prompt compiler (babble → structured, verifiable task), (c) a context agent (reads tasks + history + fildi state, comments with concrete help). If any leg is missing the system degrades: a journal with no optimizer is a notes app; an optimizer with no journal history has no context; a context agent with no structured tasks has nothing verifiable to act on.

The hard part is not the UI. It is (i) intent fidelity — the optimizer must not invent goals he did not state, and must flag ambiguity instead of guessing; (ii) verification — every structured task needs success criteria plus a check that actually runs (an outcome row, not a claim); (iii) privacy — journal text is his most personal fildi data (trade ideas, reflections, doubts), so the default must be Mac-local processing with any external-model use as an explicit opt-in.

## 3. Muse 2nd-level analysis

- **The journal is a new feedback source for the learning framework, not a side feature.** The Nov 3 GenAI survey found feedback is captured but not routed (generic /feedback is free text; only Daily News ask_why closes into the next prompt) and Step 6 retune is unbuilt (no versioned weights table; only the bounded ±25% tilt is automatic). Journal entries — market views with dates, trade ideas with reasoning, reflections graded against what happened — are the highest-signal feedback fildi has. The journal must write into the same outcome-registry shape the survey proposed (S1: ticker, surface, as_of, promise, outcome, horizon, bucket), or the learning leg learns nothing.
- **The optimizer is a trust boundary.** If it silently "improves" his goal into something else, every downstream agent works on the wrong task and he stops trusting the journal. The optimizer's output must be reviewable (show original + structured side by side), correctable (he edits the structured form), and graded (did it match his intent?).
- **The context agent must read, never rewrite.** His entries are the record. Agent comments live in a separate, attributed thread. A comment that contradicts his entry must say so plainly and cite what it read (a score, a pm_alerts row, a study result) — never silently edit his words.
- **Self-recursive learning is a research question first, a build second.** "Other people on GitHub have done it" is a hypothesis to test against real repos, not a premise. The research step must return named implementations with what is stealable and what does not transfer (most public self-improving-agent repos optimize benchmarks or coding tasks, not live-money trade recommendations under a no-AI-trading rule).
- **Adoption is the pass bar that matters.** A journal he does not write in is a dead feature. The build must be fast to open, fast to write in, and visibly useful within the first week (comments that actually help), or it will rot like any notes feature.

## 4. Use cases (concrete, with why + expected value)

- **UC1 — End-of-day reflection → a tight trade idea, checked against the book.** He babbles after the close: "NVDA feels heavy into earnings, maybe sell the put spread but the book is already long semis." Optimizer turns it into: goal (decide NVDA put-spread into earnings), success criteria (spread defined or rejected with a reason before tomorrow's open), verification (idea graded at expiry vs the Model List put rank + pm_alerts margin impact). Context agent reads the book (pm_alerts Monte Carlo, open short puts) and comments: "Book already has X short semi puts; adding this takes assignment-cash P to Y — tightens to a defined-risk spread or skip." Expected value: fewer impulsive single-name adds, every idea forced through the book-risk check he already trusts. This is the daily loop the journal exists for.
- **UC2 — A market view becomes a study, not a vibe.** He writes: "post-midterm tape feels like 2018, breadth is lying." Optimizer structures it: view (breadth divergence), testable claim (equal-weight vs cap-weighted forward returns after breadth divergences), success criteria (study result with a pass bar). Context agent proposes the study as a [quant] row via Muse (never auto-files) with the named data (breadth series, A314 regime harness). Expected value: his views stop evaporating — they become graded studies, and wrong views get killed by evidence instead of lingering.
- **UC3 — Self-recursive learning, evolved from real implementations.** Research finds how others do recursive self-improvement (named repos, e.g. online learning from graded outcomes, LLM self-critique loops, weight-update-from-grades pipelines), and the proposal says what transfers to fildi: versioned weights table + one retune rule behind admin approval (survey S2 shape), fed by journal + grade-ledger outcomes. Expected value: the learning loop stops being "measurement without retune" — the single biggest gap the Nov 3 survey named — with a design grounded in implementations that actually run, not in theory.
- **UC4 — A feature need becomes a plan, with the journal as the spec.** He writes: "I keep re-checking the same three tickers every morning, I want a watchlist that shouts." Optimizer structures it (goal, who, success criteria: opens to the three tickers with fresh data in one tap). Context agent proposes it as a plan row (via Muse) and links the journal entry as the originating evidence. Expected value: feature ideas arrive as structured plans with a real user story attached, instead of as chat fragments that get lost.

## 5. Steps

- **Step 0 — Inventory before building (verify "already covered" in code, do not assume).** Search the repo for existing journal-like surfaces: the generic /feedback endpoint, any notes fields on watchlist/positions, Daily News ask_why, the conviction ledger (A94). Report what exists, what each stores, and what the journal reuses vs builds new. If a feedback/note surface already stores free text with dates, the journal extends it; it does not build a parallel store. Deliverable: a short inventory + reuse decision, in the plan file's review tail.
- **Step 1 — Journal capture (UI + storage).** New Journal section in the fildi app, following the A305 token file and shared TabBar (no new fonts, colors, or tab chrome outside the token file). Entry editor (fast open, autosave, plain text + tickers auto-linked), entries list (reverse-chron, searchable, each entry dated and linked to that market day's brief/tape so a Nov 4 reflection sits next to Nov 4's close), entry detail (original text immutable once saved; edits append a revision, never overwrite). Storage: Mac-local Postgres, new table(s) + migration (follow the repo's migration pattern, sequential numbering). No journal content leaves the Mac in this step.
- **Step 2 — Optimizer agent (babble → structured task).** Agent 1 reads a journal entry and returns a structured task: goal (one sentence), context (the facts it used, with tickers/dates/numbers copied exactly — never rounded, never invented), success criteria (observable, with a number or a date where one exists), verification method (how success gets checked continuously — an outcome row, a grade at expiry, a book-state check — named explicitly), owner + deadline if stated, and open questions (ambiguities flagged, not guessed). Output shown side by side with the original entry; Jamie can edit the structured form; the original is never altered. Processing default: Mac-local model (OpenJev local MLX) — external-model (Haiku) processing is an explicit per-entry opt-in he toggles, never a default. If local processing cannot run (OpenJev down), the optimizer queues the entry and says so — it never silently sends journal text out.
- **Step 3 — Context agent (comments + concrete help).** Agent 2 reads the optimized task + journal history + read-only fildi state (Model List ranks, option_score, pm_alerts Monte Carlo + book, conviction ledger, recent studies). It appends attributed comments in a thread separate from his entry: (a) trade-idea check — cross-check vs fildi scores and book risk, flag contradictions with numbers; (b) portfolio safety — state plainly if an idea conflicts with book risk (assignment-cash, margin, concentration) using pm_alerts values; (c) study proposal — turn a market view into a draft [quant] study (handed to Muse for filing, never auto-filed); (d) feature proposal — turn a need into a draft plan row (handed to Muse, never auto-filed). Every comment cites its source. Comments are graded by Jamie (helpful / not) — the grade feeds the optimizer's own improvement.
- **Step 4 — Continuous verification wiring.** Every structured task writes an outcome-registry row (survey S1 shape: ticker, surface, as_of, promise, outcome, horizon, bucket) when its verification date arrives; the journal UI shows each task's live status (open / verified / failed) next to the entry. The optimizer's intent fidelity is measured on a rolling sample (Jamie confirms or corrects the structured form — corrections are logged as training signal, never discarded). Nothing in this step changes any live score, rule, or position. No AI trading, ever.
- **Step 5 — Self-recursive learning evolution (research, then proposal).** Research how others implement recursive self-improvement on GitHub: search for self-improving-agent repos, online-learning-from-grades pipelines, LLM self-critique loops, and weight-update-from-outcome systems. For each candidate (≥3, named with repo + what it does): what it optimizes, what its feedback signal is, what its guardrails are, and what transfers to fildi vs what does not (most optimize benchmarks/coding, not live-money recommendations under a no-AI-trading rule). Then propose the evolution of fildi's loop as a design (not a build): versioned weights table + exactly one retune rule behind admin approval (survey S2 shape), fed by journal outcomes + grade ledger + scoreboard verdicts, with a named baseline (today: Step 6 unbuilt, only the ±25% tilt automatic) and a measured improvement bar. **This step feeds A327 (learning loop v2, already filed) — it does not duplicate it.** If the proposal overlaps A327's scope, it lands as input to A327's review, not as a second row. No live score-input or live-money rule change comes out of this step under any outcome.
- **Step 6 — Visibility (dashboard, not backend-only).** Journal processing status is visible in Settings: entries count, optimizer queue depth + last run, comment helpfulness rate, outcome-registry rows from journal tasks, learning-loop state (what the loop has proposed vs applied — applied must always be empty without his approval). A tool/process that only exists in logs is not done. Catalog row per the verdict rule (this is a build, not a tool verdict — but the same visibility bar applies).
- **Step 7 — Reviewing agent proposes 2+ additional use cases.** The reviewing agent (Claude/Grok per the route above) reads the worked use cases UC1–UC4 and proposes at least two more concrete use cases with why + expected value, as a condition of its review — a review that proposes nothing additional is incomplete.

## 6. Downstream impact

- Model List / option_score / fund score: read-only inputs to the context agent. No writes, no score changes, no live-rule changes from any journal output.
- pm_alerts + book (watchlist_sync.pm_alerts, pm_book_latest): read-only. Journal trade ideas are checked against them; the book is never modified by the journal pipeline.
- Grade ledger / scoreboard / outcome registry: new writes (journal-task outcomes, optimizer corrections, comment helpfulness). Read by the learning loop (A327).
- ASKS rows: new rows arrive only through Muse (draft studies / feature plans handed over by the context agent), never auto-filed by the journal agents.
- UI: new Journal tab + Settings visibility rows. Follows A305 tokens; no new design language.
- OpenJev (local MLX): new consumer of the local model for optimizer processing; watch local-model load (it shares the Mac with the 48GB DiffusionGemma server — do not stack large models).

## 7. Upstream data dependencies + maintenance

- Postgres migration for journal tables (new, sequential) + outcome-registry rows. Owner: whoever builds Step 1; maintenance is the migration + a retention rule (journal is his record — no auto-prune; export path is a decision for later, not this row).
- OpenJev local model must be up for default optimizer processing; if it is down, the queue-and-wait behavior in Step 2 is the fallback (no silent external send).
- Brief archive linkage: entries link to commentary/YYYY-MM-DD-{am,pm}.md by date — depends on the brief archive continuing (it is scripted and verified).
- pm_alerts / Model List freshness: the context agent's comments are only as good as the last pm_alerts run (15 min) and Model List run — comments must carry the as-of time of the state they read.
- Maintenance: optimizer prompt version is recorded per structured task (so a bad prompt version's outputs can be identified); comment-helpfulness grades are reviewed monthly; the GitHub-research list in Step 5 gets a re-check date (public repos move fast).

## 8. Pass / fail bars

- **P1 (optimizer fidelity):** on a 10-entry sample of his real babble, ≥9 structured tasks carry a goal + success criteria + named verification method, with zero invented goals and zero invented numbers/dates/tickers (each number traceable to the entry). Fail = any invented goal, or <9/10 complete.
- **P2 (his words intact):** zero agent edits to entry text in any test; all agent output in attributed comment threads. Fail = one rewrite.
- **P3 (portfolio safety honest):** on 5 journal trade ideas run against the live book, the context agent's risk comment matches pm_alerts state (same direction, same magnitude band) on all 5, and flags at least one genuinely risky idea a human would catch. Fail = a contradiction with book risk, or zero flags on a deliberately risky idea.
- **P4 (learning evolution grounded):** Step 5 names ≥3 real GitHub implementations with transfer analysis, states the A327 overlap explicitly, and proposes a design with a named baseline + measured improvement bar. Fail = a proposal that duplicates A327, or cites no implementations, or proposes a live-score change.
- **P5 (visible + adopted):** Journal section live in the app with Settings visibility (Step 6), and Jamie writes ≥3 entries/week for 2 weeks — or he says stop. Fail = shipped but unused after 2 weeks with no comment-helpfulness signal.
- **P6 (privacy):** no journal text leaves the Mac in any test without his explicit opt-in (checked by attempting the Haiku path without opt-in — it must queue, not send). Fail = one leak. Stop rule: any privacy failure closes the row.
- **Stop rules:** any journal text leaving the Mac without opt-in → STOP, close. Any auto-filed plan/study or auto-trade → STOP, close. Any learning output touching live scores or live-money rules without his approval → STOP, close.

## 10. Non-goals

- Not a notes app for anything else, not a replacement for /feedback (Step 0 decides reuse). Not an auto-trader, not a live-score input, not a chatbot for the journal. No social/sharing features. No cloud sync of journal content in this row.
