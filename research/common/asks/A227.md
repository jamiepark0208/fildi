### Supabase facts (official docs, read 2026-10-21) — inputs for the A72 host note
- **Size:** Free = 500 MB database size per project, 2 active projects, shared CPU / 500 MB RAM, 5 GB egress. Source: https://supabase.com/pricing
- **Fildi's DB was 886 MB on 10-14** (A72, Claude plan 2026-10-14). The whole DB does not fit. Only the portable subset can go up, and A211 (c) per-schema sizes decide what fits.
- **Over the limit:** a Free project goes **read-only** past 500 MB (writes fail with SQLSTATE 25006, scheduled jobs included). There is also an org-level fair-use limit based on the *average daily* size over the billing period. Source: https://supabase.com/docs/guides/database/database-size
- **No automatic backups on Free.** Source: https://supabase.com/pricing (feature table). A nightly `pg_dump` (A72's backup line) is required, not optional.
- **Idle pause:** Free projects pause after low activity over 7 days. "Typically a few user requests to the database each day" prevents it. A warning email arrives about a week ahead, and a paused project can be restored for up to 1 year. Source: https://supabase.com/docs/guides/platform/free-project-pausing
  - The docs don't say whether in-database `pg_cron` runs count as "user" activity. Treat it as no. The keep-alive is the external daily jobs themselves (e.g. a scheduled CI runner querying the DB).
- **pg_cron:** supported on the hosted platform as "Supabase Cron". It runs SQL, or HTTP calls via `pg_net`. The docs page names no plan restriction. Recommended: ≤ 8 concurrent jobs, each ≤ 10 min. Sources: https://supabase.com/docs/guides/cron and https://supabase.com/docs/guides/functions/schedule-functions
- **Edge Functions on Free:**
  - Limits: 500k invocations/month (pricing page), 150 s wall clock, **2 s CPU per request**, 256 MB memory, 100 functions per project. Source: https://supabase.com/docs/guides/functions/limits
  - Runtime is TypeScript/Deno (Supabase docs), so it can't run the Python jobs (`scripts/watchlist_sync/*.py`). It only fits small I/O-bound TS fetchers.
  - Heavy or Python jobs stay on the CI runner or the Mac.
- **Exposure:** "A table in an exposed schema without RLS is readable and writable by any role with a grant on it." On existing projects, new `public` tables auto-grant every privilege to `anon`. Source: https://supabase.com/docs/guides/database/postgres/row-level-security
  - This drives the Security Sweep flip below.
