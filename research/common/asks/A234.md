## 2. Workstream 1 — Comms: inboxes, wake-ups, delivery receipts

Heartbeat today (`~/.fildi/agent-events.jsonl` + the Stage orb, A122) proves an agent is *alive*. It does not prove a routed row was *received*. Close that gap:

- **Per-agent inbox files** — `.agents/inbox/<agent>.md` in the repo. Any agent routing work to another appends a dated entry: row ID, what's needed, priority, link. Rule: an agent checks its inbox at session start and on heartbeat ticks, before picking up ambient work. Cheap, git-native, no new infra, survives any agent being offline.
- **Delivery receipts** — the receiving agent acknowledges a routed row by flipping its inbox entry (or the ASKS row's status note) to `ack <agent> <date>`. Un-acked high-priority entries are what the wake-up layer escalates — no ack, no assumption of receipt.
- **Wake-up layer** — two candidates, in order:
  1. **A218 Orca fleet console** (already under test as the fleet-manager candidate): if its verdict is positive, it becomes the wake/route surface — one console that can nudge the idle agent holding the relevant budget.
  2. **Fallback — tighten the repo watch:** high-priority rows un-acked or untouched escalate *same-day* (not at the current 48h aging threshold) in the watch's delivery; >5-day naming stays for normal rows. No new tooling, worse latency than (1), still strictly better than today.
- **Pass bar:** the A231 scenario rerun (see UC1) resolves in <30 min of agent-time instead of 4.5h of wall-clock neglect.

## 3. Workstream 2 — Claim locks

Extend §3b's proven pattern (claim the ID first) from IDs to *work*:

- Before building or formally reviewing a row, an agent **claims** it: status note in ASKS.md (or a single claims file if row-edit contention grows) with agent name + date. One claim per row; a second agent finding a live claim picks different work or posts a challenge in Reviews instead of starting a parallel build.
- **Claims expire** — a claim untouched for 48h (24h for high-priority) lapses and the row returns to the pool, so a dead or busy agent can't squat a row (this is the Grok-idle failure inverted: claims must decay, or locks become the new stall).
- Reviews are exempt from exclusivity — multiple reviewers are the point — but a review *claim* still registers who's reading, so three agents don't unknowingly duplicate the same deep review while another row starves.
- **Pass bar:** zero ID collisions and zero overwrite incidents across a 30-day window, measured in the monthly audit. One incident resets the count and gets a post-mortem in the calibration log (§5).

## 4. Workstream 3 — Token orchestration

The orchestrator role lands on Muse (already the queue-chaser and monthly auditor) — routing *within* Jamie's lanes, never redefining them.

- **(a) Capacity ledger.** A short table in AGENT_OPS: per agent — plan/billing type, reset cadence (Claude: 5h rolling + weekly cap; Cursor: monthly until 2026-12-11, then zero; Grok: per its plan; Codex: per its plan; Muse: continuous scheduled loops), and typical remaining-capacity signals. **Each agent reports its own capacity facts; the orchestrator never guesses a number it wasn't told.** Ledger updated when any agent's plan changes.
- **(b) Work sizing.** New rows get an S/M/L tag at filing (S = single-session review or fix; M = a study or build leg; L = multi-session program). Sizing is what lets routing match job to holder: an L build never lands on the agent with the 5-hour window; an S verification is the perfect sweep unit.
- **(c) Routing rules (within existing lanes).**
  - The [quant] gate stays Claude-only — non-negotiable, this plan doesn't dilute it.
  - When Claude's window is hot: quant work *queues* for Claude, or takes a Grok/Codex **challenge pass** first (devil's-advocate reading, edge cases, data checks) with Claude's final pass still required before anything advances. Challenge passes make Claude's eventual review *cheaper*, not optional.
  - Bulk overflow (second-pass reviews, audits, research, builds) routes to Cursor/Grok/Codex **by remaining capacity** from the ledger, not by habit.
  - Cursor's capacity gets a **planned burn-down**: because it dies Dec 11, the orchestrator front-loads Cursor-sized work (builds, its review backlog) into Nov–early Dec instead of discovering the cliff mid-queue. The Cursor-replacement thread (A199) consumes this same schedule.
- **(d) Use-it-or-lose-it sweeps.** Before a budget window lapses (Claude weekly reset, Cursor monthly, any agent reporting slack), the orchestrator feeds the holder the highest-value items from a **standing sweep pool**: useful work we currently skip for budget reasons — second-pass reviews of shipped plans, code audits of the Oct 21 permissions-audit type, backtest/study reruns on fresh data, doc and index hygiene, transcript/receipt gathering for A85/A94. Rules: the pool is pre-ranked by value; the **no-noise gate still applies** (nothing enters the pool that wouldn't change a decision or a build); a sweep never manufactures filings to burn tokens — if the pool is empty, capacity lapsing is the *correct* outcome and gets reported as such.
- **(e) Measurement.** Muse's monthly agent-ROI audit extends with: per-agent tokens spent vs lapsed (as reported, not guessed), sweep items completed and their downstream value (did the audit find anything? did the rerun change a verdict?), and routing stats (how often capacity, not priority, chose the agent). First report establishes the baseline; trends after.

## 5. Workstream 4 — Cross-training: reviews are the training signal

Nobody here fine-tunes anybody. The mechanism that already works — a review verdict changing the author's next plan — gets made systematic:

- **Calibration log.** Every review verdict that overturns or materially changes a plan writes a dated, one-paragraph lesson into a shared standards file (AGENT_OPS amendments where they change protocol; a calibration log where they teach judgment). Standing examples to seed it: the A227 rejection-challenge outcomes (which cheap-rejection patterns overturned, and why), the A179–A182 collision post-mortem, A231's "tickets don't wake anyone."
- **Context packs.** Per lane, a distilled pack an agent reads at session start: the lane's current standards, 3–5 worked examples of a pass and a fail (anonymized by row ID, not by agent — the point is the pattern), and the open calibration lessons. Packs are maintained by the orchestrator from the calibration log; they are *short* — a pack that costs more tokens to read than it saves in corrections gets cut, per the pass/fail bar below.
- **Convergence metrics** (monthly audit): % of Muse plans passing Claude review without material changes (trending up); rejection-overturn rate from A227-style challenges (trending down); collision count (= 0); median open-row idle time (trending down). These are floor metrics.
- **The goal is floor-raising, not identical agents.** Grok stays the skeptic, Claude stays the quant gate, Cursor stays the builder — diversity of vantage is the framework's value. Convergence means nobody ships *below* the bar (no bare study orders, no unexpanded plans, no cheap rejections), not that everyone writes the same plan.
- Out of scope, noted once: literal model training (LoRA on accepted diffs) already lives in the Cursor-replacement thread as a local-model option; it is not this plan's mechanism.

## 6. Use cases

- **UC1 — CI-red wake-up (the A231 rerun).** CI goes red on tip at 13:00. Under this plan: the row is filed with an inbox entry to the owning agent + claim registered; no ack within the window triggers same-day repo-watch escalation naming the row; a holder with capacity (any agent — the fix was markdown) claims and fixes. Expected value: 4.5h of red CI and a Jamie nudge → <30 min, zero Jamie involvement. This is the single most concrete win in the plan.
- **UC2 — End-of-window sweep.** Friday: Claude's weekly window has room after the queued [quant] verdicts. Instead of lapsing, the sweep pool hands over the highest-ranked queued verification (e.g., a second-pass review of a shipped plan, a permissions-style audit of one route family). Expected value: work that today *never happens* gets done at $0 marginal cost; the monthly audit reports what each sweep actually found, so the pool's ranking self-corrects.
- **UC3 — Cursor burn-down before Dec 11.** Cursor's remaining weeks are scheduled against its build/review backlog in size order, heaviest first, so the Dec 11 cliff arrives with the queue already drained to Muse/Claude/Codex-sized work. Expected value: no mid-build orphaning; the replacement decision (A199) gets real load data instead of a guess.
- **UC4 — New-agent onboarding.** Kiro (or any future roster addition) reads the context packs + calibration log and files its first plan to the house standard in session one, instead of the current pattern — weeks of corrections teaching each agent the same lessons individually (the Oct 20 study-expansion and cheap-rejection corrections were each taught the expensive way). Expected value: onboarding cost drops from repeated Jamie corrections to one supervised first filing.

## 8. Pass/fail bars (30-day window from adoption, monthly audit reports)

1. ID collisions: **0**. Overwrite incidents: **0**. Any incident = fail + post-mortem.
2. High-priority row median time-to-ack: **< 2h**; time-to-first-work: **< 12h**. (Oct 21 baseline: 4.5h for a red-CI row, with a human nudge.)
3. Token accounting: per-agent spent-vs-lapsed reported monthly, **from agent self-reports only**; sweep completions itemized *with outcomes* (found something / changed something / confirmed clean). A sweep month whose items produced zero findings across the board triggers a pool re-ranking, not more sweeping.
4. Convergence: Muse plans passing Claude review unchanged — trend up vs Oct baseline; rejection-overturn rate — trend down.
5. **Overhead check (the kill switch):** if coordination artifacts (inbox, claims, packs, ledger) measurably cost more agent-turns than the idle time and collisions they prevent, the framework gets *simplified*, not defended. The monthly audit states the coordination cost explicitly.
