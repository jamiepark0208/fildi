# A180: Pre-Dec-11 build capacity plan — rank the queue, kill the tail

**From → to:** Muse → Cursor · **Date:** 2026-10-19 · **Status:** open
**Severity:** high (the scarcest resource is build slots, not tokens)

## Thesis

Cursor's build lane expires Dec 11, 2026 — ~7 weeks out. The open queue is 15 rows
(A140–A179 index count), of which ~7 are real Cursor builds (A168, A172, A175, A176,
A177, A178, A179) plus a parked backlog that will lobby for revival. Every week a
low-EV build consumes a slot, a high-EV build (Strategy Library, runner, 0DTE data
check — the options-edge pipeline) slips past expiry. This is a capacity-allocation
problem, and right now nobody is running the math. The dev loop runs it once.

## Why now

- Dec 11 is 7 weeks away; post-expiry the build lane is Claude Code or Kiro — both
  untested at fildi build throughput. Whatever doesn't fit the window is at risk.
- A173 now requires every row to name its scoreboard number — the ranking function
  finally exists. This row applies it to the queue itself.
- Grok reviews are not free (AGENT_OPS.md: they burn Cursor credits) — the same
  capacity math constrains review volume.

## What changes (plan-level, no code)

1. **Inventory:** list every open/planned row that needs a build (Cursor or Claude),
   plus parked rows a revival would compete with.
2. **Score each:** (a) scoreboard number it moves (A171: Own−Avoid, FV cheap−rich,
   put Brier, IRA vs SPY/QQQ) × (b) confidence of movement × (c) inverse build cost
   (S/M/L, one tap from the row owner). Rows with no named scoreboard number (per A173)
   score zero until the owner names one.
3. **Capacity math:** estimate remaining build slots before Dec 11 from recent
   throughput; head-of-queue must fit. The tail gets an explicit kill/park
   recommendation.
4. **Decision:** Jamie confirms kills/parks in one review pass (the triage offer he
   already has open — this gives it the numbers).

## Use cases

- UC1: Jamie opens one ranked table and sees which 5 builds survive to Dec 11 and
  which 10 don't, with the reason in one line each.
- UC2: A175 (Strategy Library) vs A177 (0DTE data check) fight for the same week —
  the table says which moves a scoreboard number and which is optionality.

## Expected results

Quantitative: head-of-queue rows each carry a named scoreboard number and an
expected move (e.g. "put Brier −0.01 on Own-list puts" or "unblocks A176 runner").
Qualitative: zero builds land the week of Dec 7 without a named scoreboard payoff.

## Risks

- Scoring is subjective — mitigated by Jamie's final tap and by grounding cost in
  the row owner's own estimate.
- Throughput estimate is noisy — use a range (pessimistic/expected), plan to the
  pessimistic one.
- This is a one-time planning task; it must not become a recurring meeting.
