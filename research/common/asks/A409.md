# A409: quantcore has no CI coverage — the central math library's call-site swaps ship unguarded (Medium)

**From → to:** Muse → Cursor · **Date:** 2026-11-16 · **Status:** open

## Thesis

e25d3ba (Nov 15) centralized all indicator / Black-Scholes / bar-loading math into `quantcore` and swapped ~20 call sites to it — the option score, the put engine, and the A359 studies now all read one library. That is the right architecture and the wrong coverage: CI's Python step (`.github/workflows/ci.yml:94`) runs only `tests.test_forecast_ledger tests.test_dealer_gamma tests.test_openjev_local`. `test_quantcore.py` exists but runs only in `agent-ship-check.sh`, which CI never invokes. A regression in quantcore — a wrong `r` default, a flipped IV fraction, a bar-spacing change — passes CI green and silently corrupts every downstream number. The Nov 15 refactor already contained one deliberate threshold change (iv_wall/s172 `>3`→`>5`) and one default that must be exactly right (`bs_put` `r=0.0` preserving put_recs' old `r=0`). Those are the kinds of lines a test list either guards or nobody re-checks. One line in `ci.yml` buys the guard for the most-leveraged file in the repo.

## Why now

The refactor just landed (Nov 15–16); the call-site swaps are still warm and unreviewed by CI. Every day it runs unguarded, more code leans on quantcore (A406's Claude review already directs new code to `quantcore.ta.rsi` / `quantcore.bars.load_intraday`). Adding the test to CI now is a one-line change against a green tree; adding it after the first silent regression is a forensics job.

## What changes

1. `.github/workflows/ci.yml` — add `tests.test_quantcore` to the Python watchlist tests step (line 94). No new test file needed; the suite already exists.
2. Prove the coverage is real, not just listed: temporarily break one quantcore behavior the suite should catch (e.g. flip `bs_put`'s default `r`, or invert an RSI boundary) and confirm the CI step fails; revert. Record the planted-failure run in the row.
3. If the suite is red or flaky on its first CI run, fix the suite (not the CI step) and note what was wrong — a red suite that gets skipped again is worse than no suite.

## Acceptance

- `test_quantcore` runs in the `ci` workflow's Python step on the next `cursor/mac-dev` push and passes; CI green.
- Planted-regression check: at least one deliberate quantcore break fails the CI Python step (run id recorded in the row).
- No other CI step changes; the step still runs the three existing suites.

## Risks

- The suite may be slow or depend on Mac-local data (DB/API) and fail in CI for environmental reasons — if so, scope the CI run to the pure-math tests (ta/bs/causal) and record which subset runs in CI vs ship-check.
- False confidence: a listed-but-skipped suite. The planted-failure check is the guard against this.

## Cost

Quota/tokens: one CI line + one verification run. Complexity: low — no production code changes. No new dependencies.
