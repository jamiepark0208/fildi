# A317: writeEarningsHistory deletes ALL upcoming dates when the vendor returns two within 21 days

**From → to:** Muse → Cursor · **Date:** 2026-10-30 · **Status:** done

## Problem (repo-watch finding, commit 21edaa3f, B17 fix)

`writeEarningsHistory` in `artifacts/api-server/src/lib/earnings-history.ts` runs
its stale-date cleanup AFTER all upserts, in the same transaction: for each returned
upcoming row it deletes every unreported row within ±21 days of that row's date,
excluding only that row's own date.

If the vendor payload contains TWO upcoming dates within 21 days of each other,
each iteration deletes the other one, so the ticker ends up with NO upcoming date
at all — worse than the stale row the fix was removing, and self-perpetuating:
the ticker re-qualifies as "missing upcoming date" on the next fetch, re-fetches
the same two dates, and deletes both again.

## Trigger (plausible, not hypothetical)

`fetchLiveEarningsHistory` in the same file merges sources: FMP rows plus a
Finnhub `/calendar/earnings` upcoming row appended whenever its date string is
not already in the FMP set. A one-day vendor disagreement (FMP 11-17 vs Finnhub
11-18 — the exact NVDA pattern named in the B17 commit message) therefore yields
two upcoming rows in one `writeEarningsHistory` call. Same-quarter duplicates
from any other merge path hit the same loop.

## Evidence

- `artifacts/api-server/src/lib/earnings-history.ts`, `writeEarningsHistory`:
  upsert loop first, then the delete loop (`DELETE FROM earnings_calendar WHERE
  ticker = ... AND eps_actual IS NULL AND report_date <> ${date} AND report_date
  BETWEEN (date - 21) AND (date + 21)`), one iteration per returned row.
- Quarters are ~90 days apart, so the ±21-day window only ever hits duplicates of
  the same quarter — the loop's only legitimate target is a stale duplicate, and
  it cannot distinguish "stale duplicate" from "second vendor date" as written.

## Fix direction

Collect the set of upcoming dates in the returned payload first, then delete
unreported rows within ±21 days of a returned date ONLY if the row's date is not
in that set (i.e. `AND report_date NOT IN (<all returned upcoming dates>)`
instead of `<> <this iteration's date>`). One DELETE per ticker, or one per
returned date with the full set excluded — either closes the hole.

## Pass / fail

- Repro: call `writeEarningsHistory` with two unreported rows 1 day apart for one
  ticker → both rows survive in `earnings_calendar` (today: both deleted).
- Regression: the original B17 case still works — a stale unreported row (e.g.
  AAPL 10-29) with only the moved date (11-02) returned is still deleted.
- No change to reported rows (eps_actual NOT NULL) or to rows outside ±21 days.

## Severity

Medium. Data-correctness edge in the earnings-date gate: a hit ticker loses its
upcoming date permanently (until the vendor payloads agree), which feeds the
put-engine "earnings date unknown" path and refetch churn. No crash, no wrong
price — the gate degrades to unknown rather than wrong.

**Moves:** ops (earnings-date gate correctness; feeds put_recs "earnings date unknown").
