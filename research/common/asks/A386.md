## Ask
The options chain job runs 40+ min every morning, and historical chains never change — most of that time is re-fetching and re-computing immutable history. Apply A367's proven pattern (tail from the watermark, distinct-only upsert, fetch_runs metering) to the options job: profile the slow step first, fetch only the tail since the last stored date, keep a compact indexed chain table, compute from that. Jamie queued this #2 on 2026-11-08; it is not started.

## Thesis (why)
The morning data chain is the book's oxygen: list ≥ 07:00, Rankings, Live, and the put engine all wait on chains. A 40-minute job that mostly re-does immutable history is a daily freshness risk — in CPI week (CPI Tue Nov 10, CRWV Tue after close, PPI Fri Nov 13) a late chain is a late book. A367 proved the fix on every other loader; the options job is the last heavy one still full. The fix is also the cheapest token spend available: one measurement-led build, then a cheaper job every morning while Cursor is on weak models and Claude is building.

## Use cases (each with why + expected value)
1. **Morning chain lands before the 07:00 list.** Rankings/Live stop running on stale chains; the book's first look each morning is current. Expected value: the whole day's put picks rest on fresh marks instead of yesterday's.
2. **Re-runs and ad-hoc backtests compute from the indexed table** instead of re-fetching history — studies (A192, A359-class) stop paying the 40-min tax per run. Expected value: faster study turnaround on the same vendor quota.
3. **fetch_runs metering makes the next slowdown visible.** A367's before/after table (pg_stat + api_usage) gets an options-job row; the next regression shows up as a number, not a late list. Expected value: no more silent slowdowns.

## Downstream impact
- Daily pipeline (list, Rankings, Live, put engine) gets its slowest step cut; vendor quota burn falls (fewer re-fetches); A192/S1/S3-style study runs get cheaper chain reads.
- No score, pick, or Model List logic touched — this row changes how chains arrive, not what they say.

## Upstream data dependencies + maintenance
- Sources: same chain vendors as today (Schwab/Yahoo/LSEG OPRA per A192 S3) — no new vendor, no new key.
- Maintenance: the indexed table needs the same watermark discipline as A367 (fetch_guard); a split/adjustment signal must trigger a re-fetch of affected history, or restated chains go stale.

## Steps
0. **Profile first, before any rewrite:** time the job per step (vendor wait vs compute vs re-fetch) on a real morning run; report the split. Stop rule: if vendor wait dominates and tail-fetch cannot move it, close as failed validation with the numbers, not a rewrite.
1. Tail-fetch: per (ticker, expiry), fetch only dates after the last stored date; distinct-only upsert; fetch_runs row per run.
2. Compact indexed table `(ticker, as_of, expiry, strike, side)` (plus the fields the compute step reads); compute greeks/marks from it, not from re-fetched history.
3. Parity check: same morning's chains, old vs new path — row counts + sample marks must match.
4. **Reviewing agent: propose additional use cases from the worked examples above** — name any you see that are not listed, with the same why + expected-value shape, before signing off.

## Pass / fail
- P1: before/after wall time on the same morning's job reported; target ≤ 15 min (report actual, not target-as-result).
- P2: a re-run fetches 0 history rows (tail-only proven by fetch_runs + vendor-call counts).
- P3: indexed table answers a sample chain query (ticker + as_of + expiry + strike) in < 1 s.
- P4: chain parity — row counts equal and sample marks match the old path; `data_freshness.py` clean; no table goes stale.
- Stop rule: P0 shows vendor wait dominates and tail-fetch cannot move it → close as failed validation. P4 fail → do not ship.
