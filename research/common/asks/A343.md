## 1. Problem (repo-watch finding, 2026-11-05 evening run)

`propose_params()` and `apply_rationale()` disagree about what a premium move is. `propose_params` nudges one premium weight and redistributes the delta across the others (`_redistribute_premium`, renormalising so the weights still sum to 1.0). But `main()` rebuilds the challenger with `apply_rationale(CP, confirmed)`, which sets only the recorded new values and leaves every other weight at its champion value — the redistribution is lost. Consequences:

1. The stored challenger premium weights sum to 1 + (sum of the nudges), not 1.0 (e.g. one +0.02 nudge → sum 1.02).
2. When two premium keys move in one cycle, the second key's redistribution already changed the first key's value, but `why` recorded the first key's value at processing time — so the rationale stored in `model_params` can differ from the promoted weights.

Scoring impact is likely nil (`fit_model.wavg` normalises by weight sum), but the DB record and the proposal rationale misdescribe the challenger that gets scored and promoted.

Severity: low. Bookkeeping / invariant bug in the learning loop, not a scoring bug.

## 2. Evidence (branch cursor/mac-dev @ caa1c44)

- `scripts/watchlist_sync/learn.py`, `propose_params`: `prem = _redistribute_premium(prem, k, nv)` per moving key; `new["premium"] = prem` (sums to 1.0).
- `scripts/watchlist_sync/learn.py`, `apply_rationale`: `out["premium"][param.split(".", 1)[1]] = new` — no redistribution, no renormalisation.
- `scripts/watchlist_sync/learn.py`, `main()`: `NP = apply_rationale(CP, confirmed)` — the challenger inserted into `watchlist_sync.model_params` and passed to `before_after` is the `apply_rationale` version, not the `propose_params` version.
- No test asserts the premium weights sum to 1.0 after `apply_rationale` (`test_a327_stage2.py:189-190` uses it only as an input to the posterior check).

## 3. Fix direction

Make the challenger equal the proposal: either (a) have `main()` use the `propose_params` output restricted to `confirmed` moves (re-apply redistribution for exactly the confirmed keys), or (b) make `apply_rationale` reproduce `_redistribute_premium` for each confirmed premium move (in `why` order) and renormalise. (a) is preferred — one code path computes the challenger, not two. Keep the stored rationale in sync with the stored params.

## 4. Pass / fail

- New test: two premium moves in one cycle → `apply_rationale` (or the replacement path) returns premium weights summing to 1.0 (±1e-4) and equal to `propose_params`' output for the same confirmed moves.
- Single-move case: challenger premium weights sum to 1.0 (±1e-4).
- Stored `rationale` in `model_params` matches the stored `params` premium weights for the confirmed moves.
- Existing `test_a327_stage1.py` / `test_a327_stage2.py` still pass.
