## Muse's analysis
First level: the token problem is re-reading — every review re-reads files. A committable graph.json lets agents query callers/callees/paths instead of grepping and reading. Second level: this complements A332 (file splits make reads cheaper; Graphify removes reads), and the portable part matters — graph.json is a file any agent can read, including VM-side Muse. The graph goes stale (needs `graphify update` / git hooks; auto-rebuild on commit exists) and the HTML viz caps at 5,000 nodes.

## Use cases (each with why + expected value)
1. **Repo-watch / code-checked reviews query graph.json instead of re-reading files.** Measured tokens-per-review on a fixed task, before/after. Expected value: the review lane (Muse's biggest recurring burn) gets cheaper without losing findings — the measurement, not the reel's multiplier, is the point.
2. **Cursor builds on fildi with the skill installed, strict mode OFF first.** Expected value: fewer re-reads during builds. Strict mode (which can DENY Read/Grep until the graph is consulted) only if the pilot holds — it is NOT in this row.

## Downstream impact

## Steps
0. Build the graph on fildi (full repo): measure build time + node/edge count. Stop rule: build >10 min or the graph unusable at fildi scale → close as failed validation.
1. Fixed-task A/B: pick one real review task (e.g., re-run a past code-checked review); measure tokens with grep/read vs with graph queries. Same findings required — a cheaper review that misses findings fails.
2. Cursor pilot: install the skill on a fildi build; strict OFF; measure re-reads/tokens on one build.
3. Verdict: adopt (integrated + visible in Settings with a catalog row) or drop (recorded with reason). Strict mode is NOT in this row.
4. **Reviewing agent: propose additional use cases from the worked examples above** (review token cut, Cursor builds) — name any you see that are not listed, with the same why + expected-value shape, before signing off.

## Pass / fail
- P1: graph builds on fildi in <10 min; node/edge count reported.
- P2: fixed review task uses ≥30% fewer tokens with graph queries AND finds the same findings (quality parity).
- P3: Cursor pilot shows fewer re-reads on one build (direction + magnitude reported).
- P4: no Cloud, no API key, no paid tier in the pilot (code-only).
- Stop rule: P1 fail → close as failed validation. P2 fail (no measured cut, or lost findings) → drop verdict, not a retry.
